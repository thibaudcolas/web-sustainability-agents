# Expanding WSG checks and interpretation

The audit should attempt quantitative and qualitative checks, including those that require browsing, comparison and judgment. The distinction is the evidence needed and the repeatability of the decision. A qualitative criterion is not a reason to omit an audit step. An agent can inspect a user journey, compare alternatives, explain its judgment and request missing evidence; it cannot turn inaccessible implementation details into observations.

## Reference available to agents

The guideline review skill now packages the [WSG draft](https://www.w3.org/TR/web-sustainability-guidelines/) as a versioned JSON reference: 71 guidelines and all 197 success criteria, including their text, direct links, categories and accessibility/privacy/security considerations. The snapshot is the [16 October 2026 publication](https://www.w3.org/TR/2026/DNOTE-web-sustainability-guidelines-20261016/). Extraction retains a SHA-256 digest of that HTML, attribution, draft status and the applicable [W3C Software and Document License](https://www.w3.org/copyright/software-license-2023/).

This is a supporting reference, not a new specification or an alternative scoring rubric. The JSON omits introductory material, examples and additional information. Agents read the selected criterion and follow its link when context is needed. Loading all criteria into every worker would waste context and encourage superficial coverage. Read the applicable groups for the task, plus cross-cutting considerations; preserve the reference version in the review packet.

The JSON and the assessment crosswalk ship inside `sustainability-guideline-review/references/` with the [published skills](../agent-skills.md). Copies in old benchmark tasks remain frozen. Updating this reference must be followed by reviewed mapping/rubric changes and a new benchmark campaign, rather than changing the meaning of historical judgments.

## Migration of the older assessment

The [2023 assessment](https://thib.me/assessing-web-sustainability-guidelines-on-automated-testing) identifies 35 automated, 16 manual quantitative and 50 manual qualitative success criteria. All 101 now have an explicit semantic migration and candidate agent probe in `assessment-crosswalk.json`. These map to 83 current criteria across 40 guideline groups. These are **review routes**, not 101 implemented tests or 40 completely covered guidelines. Existing narrow scoring results remain tied to their original rubric.

Every crosswalk row preserves the old guideline, criterion and classification, then supplies current criterion links, a probe, an interpretation rule, an evidence access route and a status. `partial-existing-evidence` means earlier collectors provide some inputs; it does not mean the whole proposed probe has run. `candidate` means a repeatable collection/review procedure is described but still needs execution and validation. The source's six static-analysis and 125 consulting rows are outside this requested migration; source-assisted expansion can address them separately.

Old section numbers must not be reused as current identifiers. Image and video guidance has merged into [media optimization](https://www.w3.org/TR/web-sustainability-guidelines/#optimize-media-to-reduce-resource-use). Form-specific and broad accessibility checks now relate to several criteria and the [accessibility considerations](https://www.w3.org/TR/web-sustainability-guidelines/#accessibility). Script security has no equivalent standalone guideline: dependency and third-party checks cover related concerns, with the [security considerations](https://www.w3.org/TR/web-sustainability-guidelines/#security) supplying context. These mappings are project analysis, not official W3C equivalences.

## Repeatable review procedure

1. Define the user task, audience, sample, initial state and success condition. Include required consent branches and complete task states. Ask for missing context that changes what is relevant; record reasonable defaults when public-site auditing can proceed.
2. Select the current criteria and their evidence routes. Collect deterministic facts with scripts; use browser interaction or source review for the remaining observations. Preserve actions, timestamps, screenshots or DOM evidence, commands and tool versions.
3. Give the reviewer the criterion text, scoped expectation and evidence IDs. Require the observed fact, interpretation, user consequence and uncertainty to be separate. An accessibility or usability tradeoff must be considered before recommending smaller or fewer assets.
4. Reconcile disputed judgments by collecting the next discriminating observation. Agreement among models is not independent evidence about the site. Missing observations remain `cantTell`; unattempted work remains `untested`.
5. Report implemented checks, attempted checks, scoped outcomes and full-criterion coverage separately. Preserve the denominator when comparing scores. The report's next audit steps should name the missing task, source file, policy evidence or owner question that would resolve each material gap.

This follows [STAR's evaluation methodology](https://w3c.github.io/sustainableweb-ig/docs/star.html): scope, exploration, representative sampling, evaluation and reporting. Public journeys can support broad review, while complete processes and internal operations still need their own evidence. A benchmark should test whether agents choose and execute appropriate probes as well as whether they label a supplied fact correctly.

## Checks that need interpretation

| Check family                         | Deterministic or procedural input                                                             | Agent judgment and useful limit                                                                                   |
| ------------------------------------ | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Media and typography                 | Formats, KB, dimensions, glyph ranges, loading times, controls and fallback behavior          | Whether the asset helps the task; whether a smaller version preserves legibility and accessibility                |
| Journeys, forms and navigation       | Recorded actions, request totals, task completion, labels, errors and recovery                | Whether steps and fields are necessary; avoid live transactions without an authorized test environment            |
| Attention, consent and notifications | Initial/accept/reject states, prominence, reversibility, permissions and third-party requests | Whether an interaction is manipulative or distracting; a third-party domain alone is not evidence of tracking     |
| Content and document delivery        | Representative passages, headings, language, document size and print output                   | Whether users can understand and complete the task; counts alone cannot establish clarity or usefulness           |
| Code, caching and APIs               | Delivered bundles, bounded coverage, request timing, headers, warm/offline behavior           | Whether work can be deferred or removed without harm; one journey's unused code is not globally dead code         |
| Hosting and claims                   | carbon.txt, provider evidence, scope, dates, units, calculations and verification links       | Whether claims apply to this origin and period; public declarations do not prove implementation                   |
| Policies and governance              | Public documents plus optional implementation records                                         | Whether commitments are specific and applicable; missing public evidence is not proof of absent internal practice |

One notable limitation in the older classification is database querying. An agent can inspect supplied source or traces for [efficient database querying](https://www.w3.org/TR/web-sustainability-guidelines/#efficient-database-querying), but public HTTP requests do not reveal database query counts. Likewise, fingerprints are insufficient to establish every dependency/runtime version, and a public hosting claim is insufficient to verify electricity sourcing. The repeatable outcome is an evidence request or scoped uncertainty, not exclusion of these criteria from the system.

## Reproduce the reference

Save the two source pages, then run the extractor. It checks the 71/197 draft structure, the 35/16/50 assessment counts, every current mapping target, the reviewed source digests and complete row correspondence. The semantic mappings are intentionally reviewed data rather than generated by matching section numbers.

```sh
mkdir -p .audit-work/wsg-reference
curl -fsSL https://www.w3.org/TR/2026/DNOTE-web-sustainability-guidelines-20261016/ \
  -o .audit-work/wsg-reference/wsg.html
curl -fsSL https://thib.me/assessing-web-sustainability-guidelines-on-automated-testing \
  -o .audit-work/wsg-reference/assessment.html
uv run --locked --script audit/wsg_reference.py \
  --html .audit-work/wsg-reference/wsg.html \
  --assessment .audit-work/wsg-reference/assessment.html
```

A source digest mismatch requires reviewing the changed source and crosswalk, not simply removing the check. Site chrome changes can alter HTML digests without changing the assessment; retain that distinction in the review. The extractor normalizes whitespace, so apply the repository's JSON formatting before comparing the published artifact.
